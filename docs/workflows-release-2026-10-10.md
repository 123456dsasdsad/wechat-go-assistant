# 工作流升级验收记录（2026-10-10）

## 已部署

- 云端 Relay：连续收集材料、原文与来源清单、项目关联、行动清单勾选、引用对应任务的停止/补发/续聊，以及结果发送状态。
- 校园 Worker：等待问题释放执行名额；收到全部回答后重新取得名额再恢复。保持不同会话并行、同会话顺序排队。
- 校园转写：独立 Python 环境，faster-whisper base，CPU/int8/4线程；标准录音、视频音轨和微信 SILK 解码。转写模型已下载，执行时无需联网或转写 API。
- 原有 iLink 接收通道、会话、模型设置、账号配置及 SSH 通道保留。Go 程序的最低构建版本为 1.25。

## 手机复测发现与修复

原生微信语音曾在入口被拒绝：消息的编码字段为4，但实际音频带有腾讯 SILK 文件头。Relay现在优先识别实际 SILK/WAV 文件头；保留原始 SILK 字节，避免给已有WAV重复加头。回归测试覆盖缺失及不匹配的编码字段、非法PCM，以及完整入站保存流程。真实手机样例已在校园端生成中文转写。

该手机任务随后遇到模型的 `server_is_overloaded`。相同 `gpt-6.1-sol/high` 的实际Codex读取文件测试既出现成功，也出现容量错误；带询问MCP的对照亦有成功，不能据此认定所有请求失败或询问工具不兼容。短API探测成功不等于完整任务通过。

Worker现在保留Codex的稳定过载错误码，Relay显示明确的上游容量提示和“重试任务”指令；失败任务不会因微信接口接收了失败通知而显示为执行完成。错误信息只传播稳定代码，不回传供应商消息里的密钥或私有链接。此修复没有改变用户选择的模型、公开API关闭状态、代理状态或校园SSH通道。

隔离录音验收在询问MCP处确实等待了人类回答，测试接口回答B后下一次模型请求遭遇容量错误。沿原会话重试后，`gpt-6.1-sol/high`正确继续使用已收到的B，最终结果被微信接口接受。这验证了服务端等待与错误恢复，未代替真实手机引用回复的验收，也未证明上游容量问题已消失。最新完整Go测试和go vet通过。

验收使用隔离会话和虚构材料，不修改真实项目。接口接受结果包时，各原件也计为已覆盖；这仍不代表手机已读。网页可查看原件和过程，不依赖手机回复凭证。

## 仍需手机验收的项目

个人微信替代通道已实现并提供独立登录程序，正式配置保持 iLink。必须使用备用账号实际扫码，核验单条转发、合并聊天、ZIP、引用、重连及主动回传，才能启用替代入口。XML样例解析通过不代表微信已允许该账号登录或转发。

真实手机中文语音的接收和CPU转写已验证，用户已确认引用问题回复B后收到正确答复；服务器亦核对到最新B答复成功。原生语音、服务端测试接口回答和手机引用回复的证据分别记录，不能据此宣称上游容量错误已经解决。个人微信原生转发尚未标记为通过。CPU base模型的识别可能有误，原录音与时间戳保留供核对。

使用方法见[工作流说明](workflows.md)。

个人微信入口增加了直接调用接收处理器的隔离回归：仅唯一绑定的联系人私聊进入队列；其他联系人、群聊、未绑定消息和空消息均不进入助手，重复消息只保存一次。合并转发的原文、发言人和缺失ZIP原件标记在持久化、处理失败和重试后保留。这些通过项不代替真实手机原生转发验收。

备用账号扫码后，手机提示成功，但服务器未获得有效登录会话，用户也确认“登录过的设备”中没有新设备。初版只有泛化的登录失败错误；加入阶段、HTTP状态及数字返回码诊断后，实际扫码复测明确得到 `personal_wechat_login_denied; stage=confirm; http=301; ret=1203; location=false`。SDK将1203定义为“登录环境异常”；该301没有跳转地址，不能当作普通重定向处理。证据说明微信拒绝当前候选登录环境，不能据此判定该账号永久无法登录其他客户端。

诊断只保留固定步骤名称、HTTP状态、数字返回码和是否有跳转地址，不回传原始响应、登录URL、凭据或联系人列表。测试同时核验SDK仍能读取完全一致的响应字节，读取错误也不会被吞掉。最终全部Go测试、go vet及最新个人微信包的校园并发检测均通过。

候选消息接收器始终未启动，没有处理其他联系人消息，正式iLink入口保留。个人微信的单条/合并转发、ZIP、引用、重连与主动回传仍未通过真实手机验收；须先有微信允许登录的入口，才能继续这些项目。
